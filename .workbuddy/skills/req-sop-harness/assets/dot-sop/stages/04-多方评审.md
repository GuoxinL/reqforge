# 04 多方评审(SOP)

## 阶段目标
组织**多角色视角**审查需求文档,系统性识别漏洞、逻辑冲突、不可行项与遗漏,形成可闭环的问题清单,而非走过场。

## 输入(前置条件)
- 03 阶段产出的 PRD 初稿
- 参与角色:产品(作者)、研发、测试、设计、运营、合规/法务(按需)

## ✅ 该做什么(DO)
1. **会前准备**:提前至少 24 小时分发文档;评审会只讨论问题,不"念文档"。
2. **多视角并行审查**,每个角色看自己的维度:
   - 研发:技术可行性、依赖、性能、架构影响
   - 测试:用例可覆盖性、异常场景完备性、验收标准可测性
   - 设计:交互一致性、体验完整性、空/错/载状态
   - 运营/合规:口径、权限、合规红线、对外文案
3. 用**评审检查清单**驱动(完整性 / 异常覆盖 / 指标可测量 / 依赖 / 风险 / 边界)。
4. 每条评审意见按格式记录:`问题 → 影响 → 处理决定(接受/修改/驳回)→ 负责人 → 截止时间`。
5. 主动安排"**毒舌评审人**"(职责就是唱反调,找推翻理由)。
6. 评审结束输出**修订计划**,并跟进到闭环。

## ⛔ 不该做什么(DON'T)
1. **不要走过场**——"大家都没意见"通常意味着没人读过。
2. **不要让作者自评为主**——评审人必须独立阅读,不能依赖作者讲解。
3. **不要开成"念文档会"**——会上逐页念 PPT/文档 = 浪费全员时间。
4. **不要搁置分歧**——评审会结束仍无结论的问题必须有升级路径(谁拍板、何时拍板)。
5. **不要只评功能,忽略非功能与合规**(安全/隐私/合规在评审环节漏掉,后期代价最高)。
6. **不要在评审通过后又随意改需求却不重新评审**(重大变更需二次评审)。

## 产出物
- 评审记录(意见清单:问题/影响/决定/负责人/时间)
- 修订后的 PRD

## 质量门禁(Exit Criteria)
- [ ] 各角色维度均完成审查(技术/测试/设计/运营,合规按需)
- [ ] 评审意见全部有处理决定,**P0/P1 级问题清零**
- [ ] 未决问题清单存在,且每个问题有负责人与截止时间
- [ ] 修订版 PRD 已同步所有评审参与者

## 常见反模式举例
- 评审会 1 小时,45 分钟在念文档,最后"散会,没问题"——上线前才发现权限设计漏了。
- 作者 @所有人 发文档,回复"OK",没人真读 → 需求带病进入开发。
