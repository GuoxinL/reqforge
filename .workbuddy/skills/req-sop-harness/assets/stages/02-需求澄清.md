# 02 需求澄清(SOP)

## 阶段目标
通过**结构化追问**消除歧义、补全信息缺口,把隐性决策显性化,输出一份"没有模糊词、边界明确、假设已记录"的需求描述。

## 输入(前置条件)
- 01 阶段产出的需求池(原始诉求、背景、约束)

## ✅ 该做什么(DO)
1. **逐条追问六要素**:目标用户是谁?触发场景是什么?成功标准怎么衡量?失败/异常时怎样?数据从哪来?与其他功能的关系?
2. 用**结构化提问**推进:多选题、场景化提问("如果用户在弱网下点这个按钮,应该怎样?")优先于开放式闲聊。
3. 按 **MoSCoW** 分级:`必须有 / 应该有 / 可以有 / 不会有`,并给出分级理由。
4. 明确**非目标(Non-goals)**:本次明确不做什么、不修改什么——防范围蔓延的关键。
5. 把模糊词逼成数字:"快"→"< 2 秒"、"体验好"→"首次任务完成率 ≥ 80%"。
6. **显式记录假设**,标注 `[待确认]`,并指派确认责任人。
7. 关键决策**对齐到人**:记录谁拍板(决策人)、何时拍板,避免"大家都以为达成共识"。

## ⛔ 不该做什么(DON'T)
1. **不要接受"大家都懂"的模糊表述**——"懂"在每个人脑子里不一样。
2. **不要替用户脑补需求**(用户没说"要什么"的地方,写"未定义",不猜)。
3. **不要只问一轮就动笔**——关键歧义点至少追问 2~3 轮,直到置信度 ≥ 95%。
4. **不要混淆"需求"与"方案"**:澄清问的是"要解决什么问题",不是"怎么实现"。
5. **不要忽略冲突需求**:两方诉求矛盾时,记录冲突、升级决策人,而不是悄悄选一边。
6. **不要默认背景一致**:新成员、新业务线、跨团队时,重新对齐背景,别假设对方知道。
7. **不要遗漏异常路径的澄清**:只澄清正常流程、不澄清失败场景,是最常见的返工来源。

## 产出物
- 澄清记录(问题 → 答案 → 决策人 → 日期)
- 已消除模糊词的需求描述 + MoSCoW 分级表
- 非目标清单 + 假设清单(含待确认项)

## 质量门禁(Exit Criteria)
- [ ] 需求描述中不含"快速/友好/流畅/大概/可能/等等"等模糊词
- [ ] 非目标(Non-goals)已明确并获干系人认可
- [ ] 每条假设有归属(已确认 or 待确认 + 责任人)
- [ ] 冲突需求已全部升级并记录处理结果

## 常见反模式举例
- 评审会上开发问"这个页面的加载超时是几秒?"——PM 说"你们看着办" → 需求没有澄清到位。
- 产品想当然写了"支持批量删除",用户实际只想要"按条件筛选后删除" → 替用户脑补需求。
