# 06 交付集成(SOP)

## 阶段目标
让需求文档**进入研发链路并持续保持有效**:需求与任务、测试用例关联,变更受控,知识可沉淀复用。

## 输入(前置条件)
- 05 阶段产出的需求基线与门禁报告

## ✅ 该做什么(DO)
1. **同步到团队工作流**:导出/关联到腾讯文档 / 飞书 / 禅道 / TAPD / Jira 等既有平台,确保入口唯一、全员可查。
2. **建立关联映射**:需求 ↔ 研发任务 ↔ 测试用例 ↔ 验收记录,双向可查。
3. **冻结基线 + 变更控制**:需求变更走正式流程(提交变更 → 影响评估 → 审批 → 更新文档与任务),并记录变更历史。
4. **保持文档"活"**:开发过程中发现假设错误、范围调整时,及时更新文档并注明变更,避免文档与实现脱节。
5. **上线后复盘**:用验收结果 vs 需求目标做对比,记录偏差与经验;未达标的指标进入下一个迭代需求池。
6. **归档**:项目结束后,将 PRD 最终版、评审记录、变更记录、复盘结论归档到产品知识库,供后续需求引用。

## ⛔ 不该做什么(DON'T)
1. **不要把文档当一次性产物**:写完评审完就扔,两周后文档与实现完全脱节,等于没写。
2. **不要让文档与实现脱节**:陈旧文档会训练团队"别信文档",信任一旦丢失很难重建。
3. **不要随意变更已冻结需求**:任何变更都要走流程,避免"悄悄改了需求"导致测试/研发白做。
4. **不要丢失追溯链**:需求 → 代码 → 测试的映射断掉后,回归与排查成本急剧上升。
5. **不要只在立项时同步文档**:变更、版本更新时不同步 = 信息孤岛。
6. **不要跳过归档**:不复盘、不归档,团队的知识无法累积,同样的坑下次还会踩。

## 产出物
- 已同步的需求文档(单一入口)
- 需求-任务-测试用例映射表
- 变更控制记录(变更单、审批、影响评估)
- 复盘与归档文档包

## 质量门禁(Exit Criteria)
- [ ] 文档已同步到团队工作流,入口唯一且全员可访问
- [ ] 需求-任务-用例映射完整可查
- [ ] 变更记录完整(谁、何时、改了啥、影响评估)
- [ ] 复盘结论已沉淀,纳入知识库

## 常见反模式举例
- 需求文档躺在本地磁盘,开发在群里问"需求在哪?"——入口不唯一,团队各自为政。
- 开发中改了三处交互没更新文档,测试按旧文档写用例 → 上线前集体返工。
