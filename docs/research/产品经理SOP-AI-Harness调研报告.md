# 产品经理"需求整理"SOP AI Harness 调研报告

> 调研目的:为自建"辅助产品经理把需求整理成需求文档的工具"提供市场参照。
> 调研时间:2026-08-14 | 信息主要来自公开资料,定价/功能以官方最新为准。

## 一、概念界定:什么是"SOP AI Harness"

在 AI Agent 领域,业界(Anthropic、Parallel.ai 等)给出了统一的分层模型:

```
Agent = Model(模型) + Scaffold(指令/工具/格式) + Harness(执行编排层)
```

**Harness 是让 Agent 真正"跑起来"的编排层**,负责四件事:

| Harness 能力 | 说明 |
|---|---|
| Control(控制) | 任务如何拆解、编排、调度多个模型/工具调用 |
| Contracts(契约) | 必须产出什么工件、满足什么门禁(gate)、何时停止 |
| State(状态) | 跨步骤/分支/会话持久化的上下文与记忆 |
| Guardrails(护栏) | 权限、审核、可观测性、人工确认点(HITL) |

**"需求整理 SOP AI Harness" = 把 PM 写需求文档的标准作业流程(SOP)封装成 Harness**,让 AI 按固定的环节推进:需求采集 → 澄清追问 → 结构化拆解 → 评审门禁 → 交付集成,而不是一次性"吐一篇文档"。

一个典型的 PM 需求文档 SOP 可以抽象为 6 个环节(下文所有工具都落在这些环节的某种组合上):

```
① 采集(原始想法/会议/反馈)
   ↓
② 澄清(追问缺口,提升置信度)
   ↓
③ 结构化(拆成 PRD 各章节:背景/用户/指标/功能/验收)
   ↓
④ 评审(多角色视角找漏洞:技术/测试/法务/设计)
   ↓
⑤ 门禁(达到质量阈值才放行)
   ↓
⑥ 交付(导出到 Jira/Notion/Confluence,关联任务与测试)
```

## 三、关键能力维度对标(自建参考)

对 6 个 SOP 环节逐一拆解市面工具的做法,提炼"做得好"的共性:

| SOP 环节 | 领先实践 | 代表工具 |
|---|---|---|
| ① 采集 | 支持多模态输入:官网 URL、截图/线框图、会议录音、竞品截图 | PRDKit、墨刀 AI、PM Agent、Figr |
| ② 澄清 | **强制多轮追问**,设置信度阈值(如 92%→95%)才放行;问结构化选择题而非开放式 | ai-prd-generator、PRD Writer、ai-prd-workflow |
| ③ 结构化 | 模板分章节生成(背景/用户故事/指标/功能/非功能/验收/风险);**功能编号 FR-001 可测试** | PRD Writer、Idam、aqua |
| ④ 评审 | **多角色/多专家并行评审**(法务/技术/销售/设计;开发/测试/运营);自动找逻辑漏洞 | Idam(4 专家)、墨刀 AI(多视角)、ai-prd-generator(多 judge) |
| ⑤ 门禁 | 歧义分析器 + 验收标准匹配 + 证据化验证(claim-by-claim audit) | Idam、ai-prd-generator(verification report) |
| ⑥ 交付 | 导出 Jira/Notion/Confluence/Linear;关联测试用例与代码工具(Bolt/v0/Cursor) | aqua、PRDKit、prd-bin、墨刀(D2C) |

**三个最重要的行业趋势:**

1. **从"单次生成"到"上下文原生"(Context-Native)**:优秀工具不再每次从空白开始,而是沉淀"产品脑"——产品背景、用户画像、历史 PRD、竞品信息在团队内共享复用(Productboard Spark、Idam、PRDKit Knowledge Hub)。
2. **从"写文档"到"评文档 + 门禁"**:差异化竞争力在评审与验证——歧义检测、多角色审查、验收标准匹配、逐条证据审计,而非文档生成速度。
3. **从"独立工具"到"嵌入工作流"**:好的 PRD 工具必须与现有研发链路(Jira/Confluence/原型/代码)双向打通,需求变更能波及测试用例与任务。

## 四、对自建"需求 SOP AI Harness"的启示(落地建议)

综合调研,自建方案建议参考以下架构(可直接用 Dify/Coze 或 Claude Code 插件形式落地):

```
┌────────────────────────────────────────────────────┐
│ ① 采集层   表单 / 会议转写 / 截图上传 / URL 抓取    │
├────────────────────────────────────────────────────┤
│ ② 澄清层   多轮追问 + 置信度评分(≥95% 才继续)      │
├────────────────────────────────────────────────────┤
│ ③ 结构化层 PRD 模板引擎(背景/用户/指标/功能/验收)   │
├────────────────────────────────────────────────────┤
│ ④ 评审层   多角色 Agent 并行评审(技术/测试/运营)    │
├────────────────────────────────────────────────────┤
│ ⑤ 门禁层   歧义/验收标准/完整性检查,不过关打回 ②   │
├────────────────────────────────────────────────────┤
│ ⑥ 交付层   导出 Word/腾讯文档/Jira/飞书,关联原型    │
└────────────────────────────────────────────────────┘
        状态/记忆:产品知识库(用户画像、历史需求、术语表)
```

**核心设计原则(从市面工具反向验证):**

1. **澄清是质量杠杆**:与其让 AI 直接写,不如先"访谈"PM 3~5 轮,把隐性决策显性化(ai-prd-workflow 的教训:"决策应该在写代码之前离开人的大脑")。
2. **评审做成多 Agent 而不是单模型**:不同角色视角(开发可行性、测试覆盖、法务合规、运营口径)并行打分,输出"问题清单 + 置信度",比单一润色更有价值。
3. **必须有人类在环(HITL)**:所有工具都强调 final approval 由人把关;AI 负责初稿与检查,人负责决策。
4. **记忆 > 提示词**:把产品知识库(公司/行业/用户/历史需求)作为 Harness 的 State 持久层,越用越准。
5. **导出即集成**:支持导出腾讯文档/飞书/Word 的国内链路,以及 Jira/Notion 的海外链路,是落地的关键一环。

## 五、选型建议速览

| 你的诉求 | 推荐路径 |
|---|---|
| 快速上手、不想自建 | 墨刀 AI(国内,原型+PRD+评审一体)或 ChatPRD(海外) |
| 深度质量把控、评审严格 | Idam AI PRD Agent(海外)/ 墨刀 AI 评审模式(国内) |
| 已有研发体系(Jira/Confluence) | Atlassian Rovo / aqua cloud / PRDKit |
| 想按自家 SOP 定制工作流 | **Dify(自托管,推荐)或 Coze 搭建**;参考开源 ai-prd-workflow / ai-prd-generator-plugin 的流程设计 |
| 零成本开源 | prd-bin(本地)、ai-prd-generator-plugin(Claude Code 免费插件) |
| 面向国内团队协作交付 | 腾讯文档 AI / 飞书 aily + 自建工作流 |
