# 01 需求采集(SOP)

## 阶段目标
完整、客观地捕获业务意图、用户诉求与约束条件,形成**可追溯的原始需求池**,不遗漏、不加工、不预判。

## 输入(前置条件)
- 业务方口头/书面诉求、会议纪要
- 用户反馈、工单、客服记录、用户访谈/调研数据
- 数据分析、竞品分析、行业报告
- 历史需求与存量文档

## ✅ 该做什么(DO)
1. **记录原始诉求原文**,保留"谁、何时、说了什么",不提前转述/改写。
2. 标注**来源与角色**:业务方 / 用户 / 技术 / 运营 / 合规,并记录可信度(一手 vs 二手)。
3. 收集**背景三问**:为什么现在做?解决什么问题?不做的代价是什么?
4. 收集**约束条件**:时间窗口、资源投入、合规要求、技术债、依赖系统。
5. 用结构化模板登记每条需求:`编号 | 标题 | 来源 | 原始描述 | 背景 | 约束 | 优先级候选 | 关联上下文`。
6. 多渠道/多来源信息做**合并去重**,但保留追溯链(谁提供的、哪次会议)。
7. 主动补齐缺失类别:**功能需求之外**,必须询问非功能需求(性能、安全、合规、可访问性、国际化)。

## ⛔ 不该做什么(DON'T)
1. **不要只听单一来源**就下结论(业务说的 ≠ 用户需要的)。
2. **不要在采集阶段就删需求、批需求、评优先级**——先完整记录,后进入澄清阶段评估。
3. **不要只记"要什么"不记"为什么"**——没有背景的需求等于废纸。
4. **不要用二手转述替代原始记录**(转述会丢信息、带偏差)。
5. **不要把解决方案当需求**记录。用户说"加个导出按钮",需求是"我需要能离线拿到这份数据"。
6. **不要遗漏非功能需求**(性能/安全/合规类通常最容易被漏掉,返工成本也最高)。
7. **不要跳过"不做会怎样"**——它决定了需求的重要程度。

## 产出物
- 需求池(每条含:编号、标题、来源、原文、背景、约束、优先级候选)
- 来源与决策追溯表

## 质量门禁(Exit Criteria)
- [ ] 每条需求都能回答:谁提出的?在什么场景下?原始表述是什么?
- [ ] 功能需求与非功能需求都有覆盖(无类别性遗漏)
- [ ] 解决方案与需求本体未混淆(混合的已拆分标注)
- [ ] 需求池已同步给干系人确认"采集完整"(可补充)

## 常见反模式举例
- "会议开完,纪要里只有结论没有原始诉求,一周后谁都不记得当时为什么这么定。"
- "只收集了功能需求,上线前才发现没有合规审核环节,全部返工。"
