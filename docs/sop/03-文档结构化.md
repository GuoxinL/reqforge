# 03 文档结构化(SOP · PRD 撰写)

## 阶段目标
按**标准模板**产出结构化的需求文档(PRD):功能可测试、验收可执行、读者(工程师/设计师/测试)不用追问就能开工。

## 输入(前置条件)
- 02 阶段产出:已澄清的需求描述、MoSCoW 分级、非目标、假设清单

## ✅ 该做什么(DO)
1. 按固定章节撰写:**背景与目标 → 范围(含 Out of Scope)→ 用户角色与用户故事 → 功能详述 → 非功能需求 → 数据埋点 → 验收标准 → 风险与开放问题 → 参考资料**。
2. **功能编号化**:每条功能 `FR-001`、`FR-002`…,每条可独立测试、可追溯。
3. 验收标准用 **Given-When-Then** 格式(给定场景 → 当执行操作 → 则预期结果)。
4. 功能描述采用"**在哪里,做什么**"句式,一句话一个行为,按先后/主次顺序行文,一个模块写完再写下一个。
5. **主流程 + 异常流程都要写**:输入非法、超时、重试、权限不足、并发冲突、空数据。
6. 明确写 **Out of Scope**(本次不做清单),防止干系人默认"自己的功能被包含了"。
7. 指标可量化:定义北极星指标 + 护栏指标(不能变差的指标)。
8. **链接而非复制**:原型、竞品截图、历史文档、接口文档用链接引用。
9. 维护**版本历史与变更记录**(版本号、变更内容、变更人、日期)。

## ⛔ 不该做什么(DON'T)
1. **不要写形容词与模糊词**:快速、友好、流畅、安全、良好体验——全部换成可测量的表述。
2. **不要解决方案先行**:先写问题与用户价值,再写方案;写"我们要解决 X",不是"我们要做个 X 页面"。
3. **不要堆砌边角 case 写 40 页**:聚焦主用例路径,边角情况用异常流程清单覆盖即可。
4. **不要把非本需求的功能写进正文**(如"本次不做,提前知悉")——正文只表达"做什么",补充信息放参考资料。
5. **不要只写功能不写异常流程**——异常遗漏是开发返工的头号原因。
6. **不要写没有指标的"目标"**——"提升转化"必须带基线值、目标值、时间窗。
7. **不要用倒叙/破折号/括号嵌套**堆叠信息;保持正向语序,便于扫描。
8. **不要照抄旧模板不更新**:每次评审前检查章节完整性与数据时效。

## 产出物
- PRD 完整初稿(所有章节,含 FR 编号与验收标准)
- 附:需求 → 功能编号映射表

## 质量门禁(Exit Criteria)
- [ ] 章节齐全(背景/范围/用户故事/功能/非功能/埋点/验收/风险/参考)
- [ ] 每条功能有编号 + 验收标准(Given-When-Then)
- [ ] 异常路径已覆盖(非法输入/超时/重试/权限/并发/空数据)
- [ ] 所有目标与指标可测量、可追踪
- [ ] **零歧义测试**:随机抽一名工程师,只看文档能否不问问题直接开发(失败即打回)

## 常见反模式举例
- 写了 40 页 PRD 但没人读——因为全是形容词和背景描述,没有可执行的功能清单。
- "支持导出"四个字——没写格式、字段、入口、权限、失败提示,开发与测试各猜一套。
